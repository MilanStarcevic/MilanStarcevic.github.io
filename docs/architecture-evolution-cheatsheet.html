ARCHITECTURE EVOLUTION

Eight independent dimensions of system design. Parent → child reads as migration affinity, not taxonomy. Each node's small caption is the trigger: the condition that makes moving to it worthwhile.

System decomposition

  • Monolith
    Default starting point — no scaling pain yet
    • Layered monolith
      Need basic separation of concerns in one codebase
      • Modular monolith
        Teams stepping on each other inside one codebase
        • Macroservices
          Need independently deployable units, ops still simple
          • Microservices *
            Need per-team ownership and independent scaling
        • Distributed modules / service-based arch.
          Need to distribute modules before splitting teams
          • Microservices *
            Need per-team ownership and independent scaling

Internal code structure

  • Unstructured code
    Prototype stage — structure would slow you down
    • Layered architecture
      Want technical separation: UI, logic, data
      • Dependency-inverted core †
        Business logic must stay independent of frameworks
        • Hexagonal / Onion / Clean Architecture
          Need swappable adapters and a testable core
    • Feature-oriented organization
      Most changes should touch one feature, not many layers
      • Vertical Slice Architecture
        Want each feature self-contained end to end

Domain modelling

  • CRUD
    Data in, data out — no real business rules
    • Transaction Script
      Simple procedural rules, low domain complexity
      • Domain Model
        Rules getting tangled, need behavior on objects
        • Rich Domain Model
          Need to make invalid state impossible to represent
          • Domain-Driven Design
            Complex domain, need shared language with experts

Communication

  • Direct calls
    Single process — no network hop needed
    • Remote synchronous calls
      Need cross-process call with an immediate answer
      • RPC / gRPC
        Internal service-to-service, need speed and typed contracts
      • REST
        Need a widely interoperable, public-facing HTTP API
    • Asynchronous messaging
      Want to decouple sender and receiver timing
      • Queues
        Need reliable delivery to exactly one consumer
      • Publish-subscribe
        Multiple consumers each need the same event
      • Event streams
        Need an ordered, replayable event history
        • Stream processing
          Need continuous computation over live event flow
      • Event-driven architecture ‡
        Want system-wide reactive behavior, mechanism-agnostic
        • Queue-based event handling
          Reactive, but need guaranteed single processing
        • Publish-subscribe event handling
          Reactive with several independent reactors
        • Stream-based event handling
          Reactive, needs ordering and replay

Data ownership

  • Shared database
    Fast to build, tight coupling is acceptable for now
    • Schema per module
      Want logical separation without splitting services yet
      • Database per service
        Need true autonomy: independent schema, scaling, deploys
        • API composition
          Occasional cross-service query, low volume is fine
        • Replicated projections
          Need fast local reads, some staleness acceptable
        • CQRS read models
          Need read shapes optimized per use case

State modelling

  • Unified current-state model
    Reads and writes have similar shape and load
    • Command-query separation
      Read and write demands are starting to diverge
      • CQRS
        Read and write scale or model very differently
        • Shared persistence
          Want CQRS benefits without extra operational overhead
        • Separate read/write persistence
          Need to scale read and write stores independently
          • Event-sourced write model §
            Need a write-side audit trail alongside CQRS
  • Append-only change history
    Need full history of how state changed over time
    • Event sourcing §
      Need to reconstruct past state or debug via replay
      • Event sourcing with CQRS
        Need both an audit trail and fast optimized reads

Distributed transactions

  • Local transaction
    All relevant data lives in one datastore
    • Distributed workflow
      A transaction now spans multiple services or stores
      • Two-phase commit
        Need strict atomicity, can tolerate blocking
      • Saga
        Need eventual consistency without distributed locks
        • Orchestration
          Need central visibility and control of the workflow
        • Choreography
          Want services to react independently, no coordinator

UI decomposition

  • Server-rendered UI
    Simple app — SEO and simplicity matter most
    • Client-enhanced server-rendered UI
      Need some interactivity without a full SPA rewrite
      • SPA
        Need rich, app-like client-side interaction
        • Modular SPA
          Single app growing too large for one team
          • Micro-frontends
            Multiple teams need independently deployable UI pieces

Footnotes

  1. *Microservices — two paths converge on the same end state, but macroservice decomposition vs. direct module distribution leave different intermediate boundaries behind.
  2. †Hexagonal / Onion / Clean — one conceptual family built on dependency inversion around a core, expressed through different vocabulary.
  3. §Event sourcing — a persistence strategy, not a CQRS subtype. An event-sourced write model is a common combination, not a requirement.
  4. ‡Event-driven architecture — a style implementable via queues, pub/sub, event streams, or combinations of them.
